### 4e. The worklet's own overrun counter is wrong at 192 kHz (finding, measured)

`typeof performance` is `"undefined"` inside the AudioWorkletGlobalScope in this Chromium (`logs/53-worklet-clock-probe.log`), so the worklet's per-quantum timer is `Date.now()`, which steps in whole milliseconds (`v2-audio-worklet.ts:488-491,511-514`). At a 192 kHz host the deadline is 0.667 ms: **any quantum that straddles a millisecond tick reads 1 ms and is counted as an overrun**, whatever it really took. The telemetry's `overrunCount` over 9000 quanta against the block timer's true over-deadline count and the straddle probability (mean block time / 1 ms):

The counter equals the straddle probability to the digit (TS-9 192k x1: 61.8 % against a predicted 61.8 %), not the miss count. The mean `cpuLoadPercent` is still unbiased (it agrees with the block timer to 4.9 %); `overrunCount`, p95 and peak are not usable above ~96 kHz (below 128 kHz the deadline exceeds 1 ms, so a quantum that really takes under 1 ms reads 0 or 1 ms and can never exceed it, which is why every 48 / 96 kHz divider row reads 0 while real overruns do register). **What the computation says, in words.**
- **96k x1 is not dominated and dominates nothing outright, but it buys what 48k os2 buys** (the same 96 kHz-internal accuracy: -1.90 against -1.89 dB at 16 kHz on the Muff; the same cost: 0.99-1.12x) **with zero engine latency instead of 0.41 ms per slot (1.22 ms for a three-pedal chain) and a 1.33 ms quantum instead of 2.67 ms.** The one column it loses on is the SD-1's mean block time, 101 % against 91 % of a deadline half as long (11 % over the 10 % tolerance, hence "not dominated"). So **at the 96 kHz-internal tier a higher host rate is the cheaper way to buy the same accuracy in latency, at no cost in solver work.**
- **96k os2 against 48k os4 (both 192 kHz internal): the same accuracy within 0.0099 dB, the same cost (0.96-1.03x), 1.03 ms less engine latency for a three-pedal chain (0.609 against 1.641 ms) and half the quantum.** What it gives up: on the TS-9 alone the p99 goes from 78 % to 107 % of a deadline half as long (over it) and on the SD-1 from 133 to 149 %; the means are equal. With the p99 columns excluded (view 2) 48k os4 is dominated by 96k os2; with them (view 1) neither dominates: a latency-and-quantum gain against a heavier tail, in a main-thread harness where one run per cell resolves p99 only to ~20 %.
- **192k x1 against 96k os2 or 48k os4 (all 192 kHz internal): zero engine latency and a 0.67 ms quantum, at +21-52 % solver cost and a tail that is over the deadline on every pedal** (p99 Muff 157 %, SD-1 230 %, TS-9 113 %, chain 469 % of 0.667 ms) **because the Newton predictor does not run at x1** (§4b-4c). It is the only arm that removes the oversampler's latency entirely and the only one whose cost the factor-keyed predictor gate inflates.
- **96k os4 and 192k os2 (384 kHz internal): not worth their cost on this evidence.** Against the 192 kHz-internal arms they read +0.45 dB at 16 kHz *closer to the converged solution* on every pedal (the 192 kHz reference is itself ~0.5 dB low there) and are over the deadline for every pedal and the chain (means 118-212 % and 535-536 % of the deadline). 96k os4 is dominated by 192k os2 when the tails are ignored. Nothing here says the extra 0.45 dB at 16 kHz is audible.
- **48k x1 is the shipping default and is not dominated** (cheapest and zero latency); it is the only arm with every pedal's p99 under the deadline, and it is -12.34 / -4.95 / -5.66 dB at 16 kHz (Muff / SD-1 / TS-9). **The three-pedal chain is over the deadline on every arm on this box, including 48k x1.**

**The unmeasured risk of each non-dominated row** (what the table cannot tell the owner):
- **48k x1, 48k os2, 48k os4:** the 48 kHz host is the only rate every interface accepts; the oversampler latency (0.41 / 0.55 ms per slot) lengthens short delays by that much (§5a: a 4.65 ms chorus delay reads 5.02 ms at 48k os4). Risk: low; they are today's tiers.
- **96k x1 (96 kHz internal), 96k os2 (192 kHz internal), both at a 96 kHz host:** *interface support* (does the user's interface or OS audio server run 96 kHz, or silently resample to 48 kHz, in which case the browser's AudioContext honours the request and the OS undoes it: unknown from this box); *NAM and IR*: a declared-48 kHz NAM is **refused**, an unstated-rate NAM and an undeclared IR run **silently wrong** (§5c), and the player pins its context to 48 kHz (§9); *jitter*: half the quantum (1.33 ms) leaves less scheduler slack, and the 96k os2 TS-9 already shows a p99 over its deadline; *pitch ops* lose the low E at any solver rate of 96 kHz or more (§5b), which 96k x1 and 96k os2 have and so do 48k os2 and 48k os4 today; only the 48 kHz-solver arm (48k x1) keeps it.
- **192k x1, 192k os2:** all of the above, plus: a 192 kHz AudioContext is the least commonly honoured by interfaces; the 0.667 ms quantum fires 1500 times a second and leaves no slack on any pedal measured here; the worklet's overrun counter is meaningless (§4e), so a host reading it at 192 kHz would see overruns that are not there and could not see the ones that are.

**What a chooser would need to read** (host rate, factor, chain contents): the **host rate** the interface and OS actually run (not what `AudioContext` reports) and whether NAM / IR slots are present (any NAM or IR pins the host to 48 kHz unless the models state their rate and the IR its rate); the **factor** and the **internal rate** it implies (= host x factor, which sets accuracy, the tail, the pitch-tracker range and, at equal predictor state, the cost); the **chain contents**: the number of program slots (latency in ms = slots x (19.5 | 26.25) / H, **and measured chain cost ~ the sum of the slots' own: chain / sum = 0.98-1.16 across the eight arms**), whether any slot is a short delay (add the engine latency to its time), whether any slot has a `pitch-tracker` or pitch-shift op (solver rate must stay at 48 kHz), and whether **the chain's x1 cost would be inflated by the missing predictor** (x1 at 96 kHz or more).
Nothing in this table says which row to pick, and the measured block times say that on this box a three-pedal chain does not fit any arm; a per-slot cost estimate **at (host rate, factor)** is what a load-time chooser needs, and §4's numbers are the first data for it.

## 8. What this cannot prove

- **Hardware.** Every accuracy figure is agreement with the engine's own native render at some rate. The standing ceiling holds: the runtime is validated against ngspice, not a pedal, and device parameters remain the fuzz gap. Nothing here says a 192 kHz-internal render is the pedal; §2d shows even the 768 kHz render is not converged at 16 kHz (about 0.5 dB below the converged value at 192 kHz, 0.04-0.13 dB at 768 kHz by the model).
- **Real time.** Headless offline rendering is as-fast-as-possible; the block timer drives the real worklet bundle on the page's **main thread**, not an audio thread. A block time under the deadline is **necessary, not sufficient**: no device callback, no audio-thread priority, no scheduler pressure from other audio work, no hardware buffer. The only wall-clock-driven run available is the live-context run in §3b, on Chromium's fallback sink (no device is reachable: `/dev/snd` EACCES, no sound server), and it is not an interface.
- **Interface and browser latency.** Not measured and not measurable here (no device, no loopback). The owner table's latency columns are the engine's (measured) and the quantum (arithmetic); the interface buffer and the browser's output buffering are absent from them.
- **The box.** One AMD Ryzen 5 5500, `schedutil` governor (idle cores sit at 1.4 GHz and ramp under load, a variance source), swap full but not being paged (vmstat `si`/`so` 0), Chromium 149.0.7827.55, bun 1.3.14. The 1-minute load readings recorded beside each timing run include **this job's own busy thread (about 1.0)**; `top` during the series showed 87 % idle and the only busy process my own Chromium (`logs/` cpu samples in the note, §4). Timings are not portable across machines; ratios between arms are what carries.
- **One level, default controls, three pedals, the fundamental only.** 10 mV peak, SUSTAIN/Drive 0.5, 1-30 kHz sines. No full-drive sweeps, no tubes or amps, no harmonic content (at 16 kHz and a 48 kHz host every harmonic aliases onto the fundamental, which is why the probe fits only that). No source impedance (0 ohm on both sides).
- **Time-behaviour documents.** Five documents (two BBD/digital delays and one chorus delay, a phaser, a tremolo, a dynamics circuit) at five arms; TS only at the 48 k and 96 k x1 arms. It shows the solver's constants are rate-free and that the resampler latency lands in delay time; it does not exercise tap-tempo, the BBD clock path beyond `boss-dd-5`'s three modes, or the pitch ops (the pitch tracker was measured as a pure function, not on a document).
- **NAM and IR** use a synthetic `Linear` model and synthetic IRs (the repo has no `.nam` or IR asset); real NAM files and IRs, the player worklet and the workbench's own worklet copy were not run.
- **The 20 kHz and 30 kHz points** are agreement with the engine's own 192 kHz render. Above 24 kHz a 48 kHz host cannot represent the signal at all, so "the higher host rate is more accurate there" is a statement about representability, not about the pedal.
- **Mutation / sensitivity.** The negative control (C) shows the rate readback and the level check can go red; the RC fixture shows the closed-form check can tell warp from backward Euler and from the ideal analog response. They do not prove no other bug exists in the host-rate path.
- **The predictions that were wrong** are in §7 with their size: the p99 multiplier (my guess was too high), the 48k os4 delay (the resampler latency was not in P8), the 96 kHz-internal group's 0.0003 dB, and the predictor ratio for the op-amp pedals.

1. **The pitch tracker and the pitch shifter count samples** (`reference-runtime.ts:345-358`, `Engine.cpp:381-387`): window 2048, hop 256, lags 20..1024 at the SOLVER rate. Measured: the tracker loses 82.4 Hz at a 96 kHz solver rate and 110 Hz at 192 kHz (§5b). **48k os4 is already at 192 kHz**, so the phase-1 tier has it today; it is not a cost of a higher host rate over a factor.
2. **The Newton start predictor is keyed on the factor, not on dt** (`oversample > 1`: `reference-runtime.ts:4884,5554`, `Engine.cpp:2522,3078`). A 192 kHz host at x1 solves at the same dt as 48k os4 but runs **without** the predictor: 1.67 / 1.89 / 1.98 times the iterations per internal sample on the Muff / SD-1 / TS-9 (10 mV) and the cost that follows (§4). A host-rate tier would either live with that or the gate would need to key on the solver rate; a design decision for the owner, not a change made here.
3. **The worklet's `overrunCount`, p95 and peak are meaningless at high host rates.** Its clock inside the AudioWorkletGlobalScope is `Date.now()` (whole milliseconds: `typeof performance` is `"undefined"` in that scope, measured in `logs/53-worklet-clock-probe.log`; `v2-audio-worklet.ts:488-491,511-514`) against a budget of 128 / host rate; at 192 kHz the budget is 0.667 ms, so any quantum that straddles a millisecond tick reads 1 ms and counts as an overrun. On the near-free linear divider at 192k x1 the counter read 231 of 9000 quanta while the true mean block time was 3.8 % of the deadline (§4). The mean `cpuLoadPercent` is still unbiased; the counters are not. Phase 1's own caveat (whole-ms quantisation) becomes a hard failure of the counter above ~96 kHz.
4. **NAM without a stated rate and IR without a declared rate are silently wrong at any non-48 kHz host** (§5c): a model trained at 48 kHz and an IR recorded at 48 kHz are re-pitched / time-scaled by 48 000 / host rate with no error. **`SignalChain.addNode` leaves a refused NAM node in the chain as a dry passthrough** once the host catches the throw.
5. **The player pins its context to 48 kHz** (`player-engine.ts:453`) and caps IR length at 48 000 taps (`ir/types.ts:14`): the player cannot take a host rate from the page as shipped. Every route to a higher host rate is through the core worklet (no NAM / IR) or a new player change.
6. **A Web Audio context's rate is fixed at construction** (`AudioContext.sampleRate` is read-only; the API has no setter). A (host rate, factor) chooser therefore cannot "reload at another host rate" the way phase 1's chooser reloads at another factor: changing the host rate means a **new `AudioContext`**, a new worklet, a new wasm instance and a new graph, with every interface-dependent behaviour (does the OS resample, does the device accept 192 kHz) outside the page's knowledge. (Phase 1's finding that a reload while playing is unsafe applies to the factor change; a host-rate change is a heavier version of the same.)
7. **`electro-harmonix-slapback-echo` fails its declared time at 48 kHz already** (repo ratchet: WRONG-TIME at 2.58 ms against 45 ms) **and the delay-time analyser's reading of it changes with the host rate** (§5a; likely the analyser's absolute echo floor against a one-sample impulse whose area falls with the host rate, not tested): the 48 kHz figure is not a property of the pedal, and `report-delay-time.ts`'s 1 V one-sample impulse should be re-scaled by the host rate before it is used at any other.
8. **The three-pedal chain Muff + SD-1 + TS-9 is over the deadline at 48k x1** on this box, WASM console, main-thread block timer: mean 131 %, p99 147 % of 2.667 ms (§4). Admission does not see WASM program slots at any factor (phase 1 §9, finding 3), so nothing refuses it.
9. **`SignalChain` and its nodes default to 48 000** (`chain.ts:18,234`, five node initialisers): a host that builds one without `sampleRate` runs every node at 48 kHz at any context rate, silently.
